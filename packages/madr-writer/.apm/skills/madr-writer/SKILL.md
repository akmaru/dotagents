Architecture Decision Record (ADR) を書き、重要な設計判断とその理由、その判断がもたらす設計上のトレードオフ、検討した選択肢とそれぞれのpros/consなどの判断に至った経緯を記述する。

ADRを書く最大の意図は、設計判断を行った理由と、それがもたらすトレードオフを明確にして残すことである。これにより、他の開発者やエージェントが新たな設計判断を下すときに過去に下した設計判断との一貫性の検査を行い、一貫性の取れた設計を維持したり、設計判断の見直しをすることが出来る。

## ADR を書くべきとき

重要・非自明・トレードオフのある決定に対して書く: アーキテクチャの選択、ツール／依存関係の選択、横断的な規約、そして**繰り返し再燃する決定**。些細な決定や簡単に元に戻せる決定には書かない。

## 配置と採番

- 決定 1 つにつき 1 ファイル: `docs/adr/NNNN-kebab-case-title.md`（ゼロ埋めの連番）。
- **まず `docs/adr/` を読み**、次の番号と既存の慣習を把握する。ディレクトリが無ければ作成する。
- 採番は作成順。既存より論理的に前に来る基盤 ADR を挿入して採番し直す場合は、**すべての相互参照**
  （リンク・`ADR 000X` の言及・各ファイルの H1 番号）を更新すること。作業後に stale な参照が残っていないか
  grep で確認する。

## フォーマット（MADR）

下記のセクション見出しは**そのまま英語（MADR 標準）**で使う。prose（本文）はリポジトリの言語で書く
（このリポジトリは日本語）。見出しを日本語化すると既存 ADR と食い違うため、見出しは英語のまま維持する。

```markdown
---
status: accepted        # proposed | accepted | rejected | superseded by ADR-000X
date: YYYY-MM-DD
decision-makers: <名前>
---

# NNNN. <短いタイトル: 決定を一言で>

## Context and Problem Statement

<なぜこの決定が必要か。問題と力学を 2〜4 文で。何を決めなければならないかを明確に述べる。>

## Decision Drivers

* <決定を左右する力／関心事>
* ...

## Considered Options

1. <選択肢 1>
2. <選択肢 2>
    - 2.1. <下位選択肢 — 選択肢 2 が共通の土台を持ちさらに分岐するとき>
    - 2.2. <下位選択肢>

<任意の 1 行: 選択肢どうしの関係／何の軸で分かれるか。>

## Decision Outcome

選択: **<採用した選択肢>**（採用理由を続ける）。

- <具体的なルール／この決定をどう適用するか>

### Consequences

* Good: <良い帰結>
* Bad: <悪い帰結／コスト>
* Neutral: <どちらとも言えないトレードオフ>

### Confirmation

<この決定が守られているかをどう検証するか: テスト・CI・pre-commit フック・レビュー。
実在するチェックとその内容を書く — テスト／フックを実際に開いて確認してから書く。
存在しないチェックを書いてはならない。構造だけ見るテストを「内容整合の検証」と偽らない。>

## Pros and Cons of the Options

### 1. <選択肢 1>

* Good: ...
* Bad: ...

### 2. <選択肢 2>（採用）

* Good: ...
* Bad: ...

#### 2.1. <下位選択肢>（採用）

* Good: ...
* Bad: ...

## More Information

<関連 ADR を番号と相対パスでリンク。外部参照。フォローアップ。>
```

## 規約

- **Considered Options は番号付きリスト**。上位の選択肢が共通の土台を持ち、そこからさらに分岐するとき
  （例: 「ファイルを生成する」→「コミットする」か「gitignore する」か）は、対等な選択肢に並べず `2.1` / `2.2`
  として下位にネストする。
- **Pros and Cons の見出しには選択肢番号を付ける** — `### 1. …`、`### 2. …`、`#### 2.1. …` — Considered
  Options の番号と対応させ、見出しと選択肢を突き合わせられるようにする。
- 採用した選択肢には Decision Outcome とその Pros/Cons 見出しの両方で `（採用）` を付ける。
- **関連 ADR を相互リンク**する: `[ADR 0002](0002-title.md)`。
- 正直かつ検証可能に保つ。とくに **Confirmation** は実在するチェックを書く — 「テスト X が Y を検証する」と
  書くなら、テスト X を開いて実際にそうであることを確認する。記述と実コードの責務を一致させる。

## 手順

1. `docs/adr/` を読み、次の番号と慣習を把握する。
2. テンプレートから起草する。Considered Options には**実際の代替案を列挙**する — 採用案だけでなく、却下した
   選択肢とその難点こそが ADR の要点。
3. Confirmation にはコードベースと突き合わせて確認したチェックだけを書く。
4. 採番し直した場合は、stale な ADR 番号参照を grep してリンク・H1・言及を修正する。
5. 完成した ADR を実態と照らし合わせて最終レビューしてから終える。
