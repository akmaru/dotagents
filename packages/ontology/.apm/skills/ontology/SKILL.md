compatibility: Designed for Claude Code. scripts/ontology.py は Python 3.10+ の標準ライブラリだけで動く。Alloy 検証には Java 17+ が要る（Alloy の jar は初回に自動で取得する）

用語集が「語が何であるか」を定めるのに対し、このスキルは「語どうしがどう関係するか」を定める。
AI と人間の説明が食い違う原因の多くは、語の定義ではなく構造が共有されていないこと — ある語が別の語の一種か、
両者が重なりうるか、どちらかに必ず属するか、何個と結びつくか、書いていないことは「偽」なのか「未定」なのか —
にある。ONTOLOGY.md はこれを明示し、機械的に検査できる形で残す。

書式は [FORMAT.md](./FORMAT.md)、問い詰め方は [GRILL.md](./GRILL.md)、Alloy への翻訳と結果の読み方は
[ALLOY.md](./ALLOY.md) にある。例は [examples/order/](./examples/order/)。

## ファイルと道具

- **用語集**（`CONTEXT.md`）: 語の定義の正。置き場は `project-layout` スキルの決め方に従って見つける。
  書式は `grill-with-docs` の `CONTEXT-FORMAT.md`（`**語（English）**:` + 1〜2 文の定義 + `_使わない_:`）
- **ONTOLOGY.md**: 用語集と同じディレクトリに置く（複数コンテキストなら、コンテキストごとの `CONTEXT.md` の隣に
  1 つずつ）。語の定義は書かず、構造だけを書く
- **`scripts/ontology.py`**（このスキルのディレクトリにある）: 以下ではこのパスを `$ONTO` と書く

| コマンド | 何をするか |
|---|---|
| `python3 $ONTO init --glossary <CONTEXT.md> --mode markdown\|alloy` | 用語集の語から ONTOLOGY.md の雛形を作る |
| `python3 $ONTO lint <ONTOLOGY.md>` | 構造の静的検査（未定義の参照、is-a の循環、排他と包含の矛盾、兄弟の関係の書き漏れ、用語集とのずれ） |
| `python3 $ONTO verify <ONTOLOGY.md>` | lint に加え、`verification: alloy` なら Alloy で無矛盾性・帰結・事例を検証する |
| `python3 $ONTO scan <ONTOLOGY.md> <仕様や実装のパス>...` | 仕様・実装とのずれ（使わない語の使用、`code:` の識別子の消失、未登録の概念の候補）を出す |
| `python3 $ONTO alloy <ONTOLOGY.md> -o model.als` | 生成した Alloy モデルを見る（Alloy Analyzer の GUI で開いて探索できる） |

## 検証の方式を選ぶ

ONTOLOGY.md の frontmatter の `verification:` で決める。初めて作るときに `AskUserQuestion` で聞く。

- **markdown**（推奨: 語が 20 個未満、または公理を式で書く手間に見合わないとき）: `lint` の機械検査に加え、
  帰結と事例は自分が公理から推論して成否を確かめる。推論の過程を開発者に示す
- **alloy**（推奨: 公理や排他・網羅が多く、組み合わせで矛盾が出そうなとき）: 公理・帰結・事例に `alloy:` 式を
  添え、`verify` が SAT ソルバーで有界に網羅検査する。反例と、矛盾の原因になった制約の組を機械的に出せる

途中で切り替えてよい（frontmatter を書き換えるだけ。markdown で書いた命題に `alloy:` 式を足せば alloy に移れる）。
一度だけ別の方式で回すなら `verify --mode alloy` のように上書きする。

## 始め方

引数と状態で分岐する。

- **ONTOLOGY.md が無い** → 用語集の置き場を見つけ、検証の方式を聞いて `init` で雛形を作り、「grill」へ。
  用語集も無ければ、先に `grill-with-docs` か `grill-spec` で語を決めるよう勧めて止まる
- **ONTOLOGY.md があり、引数が無いか「grill」** → `verify` を走らせ、結果を元に「grill」へ
- **「sync」や、変更（仕様書・実装・用語集の差分、PR、コミット範囲）を指す** → 「sync」へ
- **「verify」/「検証」** → 「検証」へ

## grill

[GRILL.md](./GRILL.md) の問いの型に従い、開発者に問いを重ねて構造を決める。進め方は `grill-with-docs` と同じ:

- `AskUserQuestion` で 1 ラウンドにまとめて出す（1 回最大 4 問、残りは同じラウンドで続けて出す）。推奨する
  選択肢を先頭に置き、ラベルに推奨の印を付ける。他の問いの答えに依る問いは次のラウンドに回す
- フロンティアは `lint` / `verify` の指摘から作る。error を先に、次に `UNSTATED`（言っていないこと）、
  次に `status: open` / `assumed` の語と未決事項
- 問いには必ず具体例を添える（「田中商事が注文を出したら、田中商事は顧客か？」）。抽象的な「X と Y は排他ですか」
  だけでは聞かない
- コードや仕様書を読めば分かることは自分で調べ、採否だけを聞く

**書き残す。** 決まるたびにその場で ONTOLOGY.md に書き、`lint` を走らせる。溜めない。

- 新しい語が要ると分かったら、先に用語集に定義を書いてから ONTOLOGY.md に足す（用語集の書式・規則に従う）
- 開発者が具体例で答えたら、それを**事例**（`expect: possible` / `impossible`）として残す。事例は
  オントロジーの回帰テストになる
- 「X なら当然 Y のはず」という答えは**帰結**として残す。公理と区別する（帰結は公理から導かれるべきもので、
  導かれなければ公理が足りないか、見込みが誤り）
- 決めきれないものは `status: assumed`（暫定で採る）か `open`（採らない）にし、未決事項に `related:` 付きで書く
- 意図的に扱わないことは「対象外」に書く（例: 時間的な状態遷移は扱わない）
- 変更履歴に 1 行足す

フロンティアが空になり、`verify` の error と warning が 0 になったら、決めたことのまとめと未決事項を示して終わる。

## sync

仕様書・実装・用語集・開発者の理解のどれかが変わった後に、ONTOLOGY.md を追従させる。

1. **変更を集める**: 指定された差分（なければ `git diff` と、直近のコミットのうち ONTOLOGY.md の最終更新より
   新しいもの）を読む
2. **機械検査**: `lint`、`verify`、`scan <ONTOLOGY.md> <仕様書の置き場> <実装のディレクトリ>` を走らせる
3. **分類する**: 指摘と差分を次の 3 つに分ける
   - **追従するだけ**（意味は変わらない）: `code:` の識別子の改名、用語集で別名が増えた、など → その場で直して
     報告する
   - **意味が変わる**: 語の追加・削除・種別の変更、is-a・排他・網羅・多重度・公理の変更、事例の期待の反転 →
     差分の案を作り、なぜ必要か（どの仕様・コードの変更から来たか）を添えて `AskUserQuestion` で承認を取る
   - **実装・仕様の側がおかしい**: 確定した公理や事例に反する変更 → ONTOLOGY.md は直さず、どのファイルの
     どこが何に反するかを報告する。どちらを直すかは開発者が決める
4. **書き残す**: 承認された変更を反映し、変更履歴に「何を・なぜ（きっかけの変更）」を 1 行足し、`verify` を
   通す

**意味を黙って変えない。** 実装が通ること・テストが通ることを理由に、語の種別・包含・排他・多重度・公理を
承認なしに変えない。LLM はコードを通すために概念を静かにずらしがちで、このスキルはそれを止めるためにある。

## 検証

`verify` を走らせ、指摘ごとに原因を 1 つに絞って示す。読み方は [ALLOY.md](./ALLOY.md) の「結果の読み方」。

- **UNSAT**（無矛盾性・語の実例・事例 possible が成り立たない）: 示された衝突する制約の組のうち、どれを
  緩めるかを聞く
- **CHECK-FAIL**（帰結に反例がある）: 反例を具体的な言葉に直して示し（「Order$3 は取り消した注文で、
  Shipment$3 が発送している」）、足りない公理を足すか、帰結の見込みを取り下げるかを聞く
- **TOO-LOOSE**（impossible のはずの事例が起こりうる）: 実例を示し、禁じる公理を足すかを聞く
- markdown 方式では、帰結と事例を 1 つずつ、どの公理・is-a・排他から導けるか（導けないか）を平文で示す

## この ONTOLOGY.md があるリポジトリで説明を書くとき

- ONTOLOGY.md の語は、定義どおりの意味でだけ使う。上位の語と下位の語を言い換えない（「注文」と言ったら
  下書きも含む。確定したものだけなら「確定した注文」と書く）
- オントロジーに無い概念を持ち出すときは、新しい概念であることを明示する（例:「（オントロジーに無い概念）」）
- 「〜は〜に属する」「〜は〜の一種」と書くときは、ONTOLOGY.md の is-a・関係と一致させる
