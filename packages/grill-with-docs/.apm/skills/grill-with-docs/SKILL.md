ユーザーの計画・設計を、共通理解に至るまでリレントレスにインタビューする。`grill-me` と違い、このスキルは
**stateful**: 決まった用語は決まった瞬間に `CONTEXT.md` へ、3 条件を満たす決定は ADR へ、ファイルとして残す。

## インタビュー

対象を**設計木**として捉える。1 つの決定から、その決定に依存する決定が枝分かれする。

木を**ラウンド**で進める。**フロンティア**とは、前提がすべて決まっていて**今**聞ける決定の集合（まだ聞いて
いない答えを推測せずに問える質問）。フロンティア全体を 1 ラウンドで出す。質問に番号を振り、それぞれに
自分の推奨回答を付ける。ユーザーの回答を待ってから次のラウンドへ。

ラウンドの書式:

```
❓ **Q1** - **<質問の題>**: <本文。複数段落や選択肢を含んでよい>

➡️ <自分の推奨回答>

---

❓ **Q2** - **<質問の題>**: <本文>

➡️ <自分の推奨回答>
```

ユーザーの回答で木の形が変わる。決まった決定がフロンティアを外へ押し出し、それに依存していた質問が解放される。
フロンティアを計算し直して次のラウンドを出す。**同じラウンドでまだ開いている質問に答えが依存する質問は、
今のラウンドではなく後のラウンドに回す。**

**事実を集めるのは自分の仕事で、ユーザーの仕事ではない。** フロンティアの質問が環境の事実（ファイル、コード、
ツールの挙動）を必要とするなら、ユーザーに聞かず自分で調べる。調べ物で全体を止めない: 調査中のものは
「未確定の前提」なので、それに依存する質問だけを待たせ、残りのフロンティアは今出す。**決定はユーザーのもの。**
1 つずつ提示して待つ。

フロンティアが空になったらセッションは終わり: 設計木のすべての枝を訪れ、黙って仮定したものが残っていない
状態。ユーザーが「共通理解に至った」と確認するまで、実装には進まない。

## ドメインモデリング（用語と決定を書き残す）

設計しながら、プロジェクトのドメインモデルを能動的に組み立て、研ぎ澄ます。用語に異議を唱え、境界を突く
シナリオを発明し、用語集と決定を**結晶化した瞬間に**書く。

### ファイル構成

ほとんどのリポジトリは単一コンテキスト:

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

直下に `CONTEXT-MAP.md` があれば複数コンテキスト。マップが各コンテキストの所在を指す（書式は
[CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)）。

ファイルは**遅延して**作る: 書くものができたときだけ。`CONTEXT.md` が無ければ最初の用語が決まったときに、
`docs/adr/` が無ければ最初の ADR が要るときに作る。

### セッション中にやること

- **用語集に照らして異議を唱える。** ユーザーが `CONTEXT.md` の既存の言葉と食い違う使い方をしたら、その場で
  指摘する。「用語集では『キャンセル』を X と定義していますが、今は Y の意味で使っていませんか。どちらですか」
- **曖昧な言葉を研ぐ。** 曖昧・多義の言葉には、正確な正典の用語を提案する。「『アカウント』は Customer と
  User のどちらですか。別物です」
- **具体的なシナリオで試す。** ドメインの関係が話題になったら、境界を突く具体的なシナリオを発明して、
  概念の境界を正確に言わせる。
- **コードと照合する。** ユーザーが「こう動く」と言ったら、コードがそう言っているか確かめる。矛盾があれば
  出す。「コードは注文全体をキャンセルしますが、今『部分キャンセルはあり得る』と言いましたね。どちらが正しい
  ですか」
- **`CONTEXT.md` をその場で更新する。** 用語が決まったらすぐ書く。溜めない。書式は
  [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)。`CONTEXT.md` は用語集であって、仕様でも走り書きでも
  実装上の決定の置き場でもない。実装の詳細は一切入れない。

### ADR は控えめに

ADR を提案するのは、次の **3 つすべて**が真のときだけ:

1. **戻しにくい**: 後で考えを変えるコストが無視できない
2. **文脈なしでは意外**: 将来の読者が「なぜこうしたのか」と思う
3. **実際のトレードオフの結果**: 本物の代替案があり、特定の理由で 1 つを選んだ

1 つでも欠けていれば書かない。戻しやすいなら戻せばよい。意外でないなら誰も理由を問わない。代替案が
無かったなら「当たり前のことをした」以上に記録することがない。

**書式は MADR**（このリポジトリの ADR の正典。`madr-writer` スキルがあればそれを呼ぶ）。`docs/adr/` を読んで
次の連番を取り、`NNNN-kebab-case-title.md` に `Context and Problem Statement` / `Decision Drivers` /
`Considered Options` / `Decision Outcome`（Consequences・Confirmation を含む）/ `Pros and Cons of the Options` の
見出しで書く。本文はリポジトリの言語で。セッション中に出た却下案と判断軸をそのまま Considered Options に
入れる。決まった瞬間に書き、溜めない。

## セッションの終わり

下したすべての決定を簡潔にまとめる。あわせて、`CONTEXT.md` に足した用語と、書いた ADR を一覧にする。
3 条件を満たさなかった決定は会話の中にしか残らないので、まとめに必ず入れる（用語集は用語集であって
仕様ではない。ADR は多くのセッションで 0 件になるのが正常）。
