# CONTEXT.md の書式

## 構造

```md
# {コンテキスト名}

{このコンテキストが何で、なぜ存在するかを 1〜2 文で。}

## 用語

**注文（Order）**:
{その用語の 1〜2 文の説明}
_使わない_: 購入、トランザクション

**請求書（Invoice）**:
納品後に顧客へ送る支払いの要求。
_使わない_: 請求、支払い依頼

**顧客（Customer）**:
注文を出す人または組織。
_使わない_: クライアント、購入者、アカウント
```

## ルール

- **態度を決める。** 同じ概念に複数の言葉があるなら、いちばん良いものを 1 つ選び、残りは `_使わない_` に並べる。
- **定義は短く。** 最大 1〜2 文。何を**するか**ではなく何**であるか**を書く。
- **このプロジェクトの文脈に固有の用語だけ。** 一般的なプログラミング概念（タイムアウト、エラー型、ユーティリティの
  パターン）は、プロジェクトが多用していても載せない。足す前に「この文脈に固有の概念か、一般的な概念か」を
  問い、前者だけを載せる。
- **自然な塊ができたら小見出しで分ける。** 全部が 1 つのまとまりなら平らな一覧でよい。
- **実装の詳細を入れない。** `CONTEXT.md` は用語集であって、仕様でも、走り書きでも、実装上の決定の置き場でもない。

## 単一コンテキストと複数コンテキスト

**単一コンテキスト（ほとんどのリポジトリ）**: リポジトリ直下に `CONTEXT.md` を 1 つ。

**複数コンテキスト**: リポジトリ直下の `CONTEXT-MAP.md` に、各コンテキストの所在と関係を書く。

```md
# コンテキストマップ

## コンテキスト

- [注文](./src/ordering/CONTEXT.md): 顧客の注文を受け付けて追跡する
- [請求](./src/billing/CONTEXT.md): 請求書を発行し支払いを処理する
- [出荷](./src/fulfillment/CONTEXT.md): 倉庫でのピッキングと発送を管理する

## 関係

- **注文 → 出荷**: 注文が `OrderPlaced` イベントを出し、出荷がそれを受けてピッキングを始める
- **出荷 → 請求**: 出荷が `ShipmentDispatched` イベントを出し、請求がそれを受けて請求書を作る
- **注文 ↔ 請求**: `CustomerId` と `Money` の型を共有する
```

どちらの構造かは推定する:

- `CONTEXT-MAP.md` があれば、それを読んでコンテキストを見つける
- 直下の `CONTEXT.md` だけなら単一コンテキスト
- どちらも無ければ、最初の用語が決まったときに直下の `CONTEXT.md` を作る

複数コンテキストがあるとき、今の話題がどれに属するかは推定する。分からなければ聞く。
