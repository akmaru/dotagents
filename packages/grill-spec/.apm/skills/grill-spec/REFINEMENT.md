# リファインメントの手順

`SKILL.md` の「終わり」で「至った: リファインメントに回す」が選ばれたら、このファイルを読み込んでから
実行する（長い grill の終盤でコンテキストの圧縮により指示が落ちるのを避けるため、実行の直前に読む）。

## 1. 周回を running で台帳に書く

起動する前に、台帳（SPEC-FORMAT.md 参照）に周回 `R<N>` を `running` 状態で書く。`N` は、台帳に残っている
周回の番号と、作業ディレクトリに既にある `r*-consistency.md` / `r*-opposing.md` の両方を見て、どちらより
大きい番号にする（台帳が失われていても報告ファイルが残っていることがあるため）。

## 2. 2 つの `general-purpose` サブエージェントを並列に起動する

観点ごとに 1 つ、合計 2 つの `general-purpose` サブエージェントを並列に起動する。依頼文に入れるのは次の
4 つだけ:

1. 仕様書・用語集（複数あれば全部）・仕様書が参照する ADR の絶対パス
2. 「仕様書に書いてあることは確定済みとみなす。制約の行を覆す指摘なら、修正ではなく反対意見として明示する」
3. 観点の固定文（下記）
4. 報告の書式（下記）

仕様書の外で作った決定の要約や、この grill の会話で出た他の文脈は渡さない。サブエージェントにファイルの
変更をさせない（Edit・Write を使わせる指示を含めない）。報告はファイルに書かせず、サブエージェントの
最終メッセージで受け取る。

### 観点 A: 整合

> 仕様書の中の整合だけを見る。曖昧さ・矛盾、課題・ストーリー・ジャーニー・受け入れ基準の対応漏れ、合否を
> 1 通りに判定できない受け入れ基準、用語集や ADR との食い違いを指摘する。

報告の書式:

```markdown
### C<n>
- 場所: <仕様書内の行番号>
- 引用: <該当箇所の短い引用>
- 制約の行を覆すか: はい / いいえ
- 問題: <何が整合しないか>
- 求める変更: <どう変えるべきか>
- 意味を変えない修正か: はい / いいえ
```

### 観点 B: 反対の立場

> 仕様書の決定に反対の立場から、懸念・批判・代案を指摘する。指摘ごとに重要度（致命的 / 重要 / 軽微）を
> 付ける。

報告の書式:

```markdown
### O<n>
- 重要度: 致命的 / 重要 / 軽微
- 場所: <仕様書内の節・行>
- 引用: <該当箇所の短い引用>
- 制約の行を覆すか: はい / いいえ
- 問題: <何が懸念・批判か>
- 求める変更: <どう変えるべきか>
```

## 3. 報告を保存する

返ってきた報告をそのまま、`.claude/grill-spec/<仕様書のパスから拡張子を除いたもの>/r<N>-consistency.md`・
`r<N>-opposing.md` に保存する。ディレクトリがまだ `.gitignore` されていなければ、ディレクトリ直下に `*`
だけの `.gitignore` を置く。

600 秒無応答などで止まった観点があれば、止まった側だけを起動し直す（止まっていない側の報告は使い回す）。

## 4. 振り分ける

- **判断の要らない修正**: 何を作るか・受け入れ基準の合否・スコープを変えない指摘（誤字、番号や参照の食い違い、
  書式の違反、主語や範囲を変えない用語集の語への置き換え）。その場で仕様書に反映し、一覧で示す
- **判断の要る指摘（1 件ずつ聞く）**: 反対の立場の致命的・重要な指摘、制約の行を覆す指摘（重要度にかかわらず）、
  整合の観点の指摘
- **判断の要る指摘（一覧でまとめて聞く）**: 反対の立場の軽微な指摘
- **どちらか迷うもの**: 判断の要る側に入れる

振り分けたら、質問を出す前に、判断の要る指摘をすべて台帳の「未回答の指摘」に `open` で書く（答えを
待つ間にセッションが切れても失われないようにするため）。答えが出たら `adopted` / `rejected` に更新する。

1 件ずつ聞くときの選択肢は `採用` / `却下: <想定理由 A>` / `却下: <想定理由 B>` の形にし、推奨を先頭に置く
（SKILL.md の「ラウンド」と同じ `AskUserQuestion` の書式）。開発者が選んだ選択肢のラベルを、そのまま採否の
理由として記録する。

## 5. 却下の行き先

- 何を作るかについての決定にあたる却下 → 仕様書の制約に `この grill で決定: <理由> / 却下案: <内容>` の形で
  書く
- 仕様書の書き方への指摘の却下、理由を聞かずに一括で却下したもの → 台帳の「台帳に残す却下」に残す

## 6. 出典を添えて台帳を更新する

判断の要る指摘を聞く質問と、反映した修正・軽微な指摘の一覧には、その指摘が書かれた報告の絶対パスと行
（または見出し `### C<n>` / `### O<n>`）を添える。すべて答え終わったら、台帳の周回 `R<N>` の行を
`running` から結果（1 件ずつ何件・採用何件、軽微何件、修正何件）に更新する。
