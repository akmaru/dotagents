# 仕様書の書式

仕様書は `docs/internal/specs/NNNN-<kebab-case の機能名>.md`（置き場・ファイル名の決め方は SKILL.md の
「調べる」）に、この書式で書く。

## front matter

```yaml
---
status: draft   # draft | accepted | revising
date: 2026-10-10 # 最後に確定した日。まだ一度も確定していない draft では作成日
---
```

## 題と用語集へのリンク

```markdown
# <題>

この仕様書の用語は [用語集](<相対パス>) に従う。
```

仕様書で使うプロジェクト固有の語は、すべて用語集に定義があること。

## 節の順

1. **課題（P）** — 誰の何が困っているか。ID: `P1`, `P2`…
2. **ユーザーストーリー（S）** — 「〜として、〜したい（→ 課題 ID）」。主語は人間だけ。ID: `S1`, `S2`…
3. **ユーザージャーニー（J）** — 目的を果たすまでの手順。複数あれば `### J1: <題>（→ ストーリー ID）` のように
   見出しを分ける。全体の流れ（ジャーニーをまたぐ入口・分岐）を書くなら `### 全体の流れ` を一番先に置く
4. **受け入れ基準（AC）** — 全体にかかるものと、各ジャーニーの手順にかかるものを両方持つ。ID: `AC1`,
   `AC2`…（ジャーニーをまたいで連番）。手順にかかるものは見出しに節を分け、各項目に手順番号を
   `**AC8**（手順1）` のように添える
5. **非機能要件** — grill で性能・容量・時間のいずれかについて数値の要求が出たときだけ持つ節。出なければ
   節自体を作らない
6. **スコープ外** — その仕様書では作らないと明示したもの。別の仕様書にすべき話題はここに
   `**未作成の仕様書: <題>（<トラッカー>: <ID>）** — 決まった点: <内容>` の形で書く（issue を作らなかった
   ときは括弧を省く）
7. **制約** — 各行に出典が要る。出典は ADR へのリンク、または
   `この grill で決定: <理由> / 却下案: <内容>` のどちらか
8. **設計上の論点（D）** — 決めていない実装方法・技術選定の問い。ID: `D1`, `D2`…

節の構成はこの順を変えない（指示ファイルの規約や既存の流儀に合わせるのは置き場とファイル名の形式だけ）。
仕様書本体には、front matter・題・用語集へのリンクと上の節以外を書かない。作業の途中の状態は台帳に書く。

## ID の振り方

- 接頭辞は P / S / J / AC / D で固定。言語によらず同じ
- 置き場・仕様書を単位にそれぞれ 1 から連番
- 改訂で ID を振り直してよい。振り直したら、その仕様書の ID を参照している ADR・ワークフローグラフの
  台帳・他の仕様書と、この仕様書自身の台帳の参照も、新しい ID に張り替える

## 対訳表

仕様書・用語集は導入先リポジトリの言語で書く（判定方法は SKILL.md の「調べる」）。決まり文句・見出しは
言語ごとに揃える。ID の接頭辞（P/S/J/AC/D）と `status` の値（`draft`/`accepted`/`revising`）は言語に
かかわらずそのまま使う。用語集が既にあるときは、新しく作らずその用語集の言語・決まり文句に合わせる。

| 日本語 | 英語 |
|---|---|
| 課題 | Problems |
| ユーザーストーリー | User Stories |
| ユーザージャーニー | User Journeys |
| 受け入れ基準 | Acceptance Criteria |
| 非機能要件 | Non-Functional Requirements |
| スコープ外 | Out of Scope |
| 制約 | Constraints |
| 設計上の論点 | Open Design Issues |
| 用語集の `## 用語` | `## Language` |
| 用語集の `_使わない_` | `_Avoid_` |

## 台帳の書式

台帳は `.claude/grill-spec/<リポジトリのルートから見た仕様書のパスから拡張子を除いたもの>/ledger.md`
（作る時点は SKILL.md の「書き残す」）に Markdown で書く。このディレクトリはバージョン管理しない
（gitignore されていなければ `*` だけの `.gitignore` を置く）。

```markdown
---
spec: <リポジトリルートから見た仕様書のパス>
---

# <仕様書のファイル名（拡張子なし）> の台帳

## 版
- v1: draft 作成 <date> / 確定 <date>
- v2: revising 開始 <date> / 確定 <date>（リファインメント N 周。報告は r1-*.md・r2-*.md）

## 変えたい点
- [vN-W<n>] open|adopted|rejected|withdrawn: <内容>

## 周回
- [R<N>] vN <date>: r<N>-consistency.md / r<N>-opposing.md — running
<!-- 終わったら次の形に更新する -->
- [R<N>] vN <date>: r<N>-consistency.md / r<N>-opposing.md — 1件ずつ<件数>件（うち採用<件数>、仕様を変えた採用<件数>）、軽微<件数>件、修正<件数>件

## 未回答の指摘
- [R<N>-C<n>|R<N>-O<n>] open: <内容>（<報告のパス>:<行>）

## 台帳に残す却下（仕様書の書き方への指摘・一括却下）
- [R<N>-C<n>|R<N>-O<n>] rejected: <内容>

## この版で触ったファイル
- <path>

## この版で作った issue
- <トラッカー>: <ID> — <題>

## 振り分けた発言
- vN: 「<発言>」 → <振り分け先（制約 / 設計上の論点 / スコープ外 など）>

## 足した用語
- vN: <用語>, <用語>…
```

- 指摘 ID は `R<N>-C<n>`（整合の観点）/ `R<N>-O<n>`（反対の立場）。`N` は周回番号、`n` はその周回・観点の
  中の連番
- 指摘の状態は `open`（未回答）/ `adopted`（採用）/ `rejected`（却下）/ `fixed`（判断の要らない修正として
  その場で反映済み）
- 変えたい点の状態は `open` / `adopted` / `rejected` と、改訂をやめたときの `withdrawn`（取り下げ）
