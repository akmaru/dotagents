仕様書・台帳の書式は [SPEC-FORMAT.md](./SPEC-FORMAT.md)、用語集の書式は
[CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)（`grill-with-docs` と同一）、リファインメントの手順は
[REFINEMENT.md](./REFINEMENT.md) にある。`REFINEMENT.md` は実行する直前に読み込む。

## 始め方

引数を解釈し、分岐する。

- **引数が仕様書を指さない**（新しい要望だけ） → 新規仕様書。status: draft で始める（下の「調べる」から）
- **draft / revising の仕様書のパスを指す** → その続き。置き場も status も変えない。続きのフロンティアは、
  仕様書の空の節、「終わり」のチェックリストで満たさない項目、台帳の未回答の判断の要る指摘から作る。
  変えたい点も渡されていれば、それについての問いを加える。台帳が見つからなければ（別のマシン・worktree）、
  失われたことを示し、リファインメントにもう一度回すかを聞く。台帳に `running` のまま残った周回があれば、
  作業ディレクトリに保存済みの報告を取り込み、報告の無い観点だけを `REFINEMENT.md` に従って起動し直す
- **accepted の仕様書のパス + 変えたい点を指す** → 「改訂」から始める
- **accepted の仕様書のパスだけを指す** → 変えたい点を聞いてから「改訂」を始める

## 調べる

質問を出す前に、ファイルやコードを読めば決まることは自分で調べる。開発者には、調べれば分かることを聞かず、
採否の判断だけを聞く。

- **置き場**: 優先順は「指示ファイル（`CLAUDE.md` / `AGENTS.md` など）の規約 → 既存の仕様書の流儀 →
  既定の `docs/internal/specs/`」
  - 規約があり、話題の単位への割り当てが 1 つに決まる → そこに書く（聞かない）
  - 規約の単位が当てはまらない、または 2 つ以上当てはまる → 聞く
  - 規約が無く既存の流儀がある → 従うかを最初のラウンドで聞く（従うなら置き場とファイル名の形式だけ合わせ、
    節の構成は SPEC-FORMAT.md のまま変えない）。従わないなら置き場を聞く（推奨: `docs/internal/specs/`）
  - どちらも無い → `docs/internal/specs/` に書く
  - 決めた置き場に draft / revising の仕様書が 1 つ以上あれば、全部のパスと題を示し、どれかの続きにするか
    新規にするかを最初のラウンドで聞く
- **ファイル名**: 採用した規約・流儀がファイル名の形式を決めていなければ `NNNN-<kebab-case の機能名>.md`。
  連番は置き場ごとに 0001 から
- **言語**: 指示ファイルに文書の言語の指定があれば従う。無ければ、導入先リポジトリの既存文書（用語集・
  仕様書・ADR・README）の本文の多数派の言語で書く。文書が無いか拮抗していれば聞く。用語集が既にあれば、その
  用語集の決まり文句と見出しに合わせる（1 つの用語集の中で言語を混ぜない）
- **用語集の置き場**: `CONTEXT-MAP.md` があれば、コンテキストの説明を見て「共通」のコンテキストと今の話題の
  コンテキストを判定する。複数のコンテキストで使う語は共通のコンテキストに置く。共通のコンテキストが
  見つからなければ聞く

## ラウンド

`AskUserQuestion` でまとめて出す。1 回最大 4 問、フロンティアが 5 問以上あれば同じラウンドの中で続けて
4 問ずつ出す。推奨する選択肢を先頭に置き、ラベルに推奨の印を付ける。他の問いの答えに依る問いは、今の
ラウンドではなく次のラウンドに回す。質問文には、その判断の根拠にしたファイル・既存文書の絶対パスを添える
（開発者が自分で確かめられるように）。開発者の発言が、読み込んだ用語集・ADR・コードと食い違ったら、その
食い違いを示す質問を次のフロンティアに入れる。

## 書き残す

決まるたびにその場で書く。溜めない。セッションを途中で打ち切っても、それまでに決まった内容はファイルに
残る。

- 用語が決まったら用語集に（`CONTEXT-FORMAT.md`）
- 節の内容が決まったら仕様書に（`SPEC-FORMAT.md`）
- 機能名が変わったら、連番を保ったままファイル名を変え、台帳のディレクトリも新しいパスに対応する場所へ
  移し、この仕様書を参照する ADR・ワークフローグラフの台帳・他の仕様書の参照も新しいパスに張り替える
- 開発者の発言が実装の技術選定・内部構造・実装手順に触れたら、制約（出典が要る）か設計上の論点のどちらかに
  振り分けて書く。他スキルやエージェントとの取り決めも同様（ストーリーの主語にはしない）
- 別の仕様書にすべき話題が出たら深追いせず、今の仕様に戻る。スコープ外に
  `未作成の仕様書: <題> — 決まった点: <内容>` として記録する。リポジトリが issue トラッカーを使っている
  （指示ファイルが名指し、`.beads/` がある、GitHub か GitLab の issues が有効）なら、作ってよいかを確かめて
  issue を作り、ID を括弧に添える。どのトラッカーに当たるか曖昧なら聞く

## 終わり

フロンティアが空になったら、次のチェックリストをすべて確認する。満たさない項目があれば、それを次の
フロンティアにして「ラウンド」へ戻る。

- すべての課題を指すストーリーがある
- すべてのジャーニーの手順に対応する受け入れ基準がある
- 受け入れ基準の各項目の合否を 1 通りに判定できる（「適切に」「など」「十分に」のような語を含まない。
  判定方法を設計上の論点に回し、その受け入れ基準から論点 ID への参照があれば満たしたとみなす）
- 制約のすべての行に出典がある
- 仕様書で使うプロジェクト固有の語が、すべて用語集に定義されている

満たしたら、共通理解と次の行き先を 1 問で `AskUserQuestion` に聞く。選択肢は「至った: リファインメントに
回す」「至った: 確定する」「まだ詰める」の 3 つ（改訂中は「改訂をやめる」を加えた 4 つ）。先頭の推奨は、
直前のリファインメント（整合・反対の立場の両方）で開発者が採用した指摘のうち、何を作るか・受け入れ基準の
合否・スコープを変えたものが 0 件なら「確定する」、それ以外（この版でまだリファインメントを通していない
ときを含む）は「リファインメントに回す」。

- **「まだ詰める」** → 詰めたい点を自由記述で聞き、それを次のフロンティアにする。status は変えない
- **「リファインメントに回す」** → `REFINEMENT.md` を読み込んで実行し、終わったら振り分けた判断の要る指摘を
  フロンティアにして「ラウンド」に戻る
- **「確定する」** → status を `accepted` にし、`date` を確定日にする。決定のまとめ、制約・設計上の論点に
  振り分けた発言の一覧、足した用語、未作成の仕様書を示して終わる。確定の前に後段（設計判断・ADR・実装）の
  作業には進まない
- **「改訂をやめる」**（改訂中のみ） → 下の「改訂をやめる」へ

## 改訂

accepted の仕様書 + 変えたい点で始まったら、status を `revising` にし、変えたい点を台帳に残して次の
フロンティアにする。以降は「調べる」〜「終わり」を J1 と同じ手順で踏むが、置き場は聞き直さない。ID を
振り直したときは、その仕様書の ID を参照している ADR・ワークフローグラフの台帳・他の仕様書と、台帳自身の
参照も、振り直した後の ID に張り替える。「確定する」を選んだら status を `accepted` に戻し、`date` を
確定日にして、変えた点のまとめ・振り分けた発言・足した用語・改訂中に足した未作成の仕様書を示す。

## 改訂をやめる

台帳の「この版で触ったファイル」に記録したファイル（仕様書・用語集・参照を張り替えたファイル・改名）を、
最後に accepted だったコミットの内容に戻し、status を `accepted` にして、台帳の変えたい点をすべて片づけた
（取り下げ）状態にする。この版で作った issue は消さずに一覧で示す。accepted のコミットが見つからなければ
戻さず、そのことを示してどうするか聞く。
